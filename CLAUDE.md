## Что это

Персональный трекер привычек. Список привычек + сетка дней, отметил день —
привычка сделана. Интерфейс русский, тёмный, под телефон.

Хронологически **первый проект портфолио** и первый опыт с Supabase и GitHub
Pages. `networth-tracker` ссылается на него как на уже имеющийся опыт — в его
`DECISIONS.md` habit-tracker упоминается как «соседний проект с привычками», от
которого отталкивались при выборе способа входа и отдельного Supabase-проекта.

Версия `1.0.0`, задеплоен, используется. Развития не требует.

Оформление зашито прямо в [index.html](index.html), не в компонентах: фон
`#131319`, системный шрифт (`-apple-system`, `Segoe UI`, `Roboto`),
`html, body, #root { height: 100% }`. Вместе с `viewport-fit=cover` это значит,
что верстался он в первую очередь под мобильный браузер на весь экран, с учётом
«чёлки» на iPhone ‹проверить по src/›.

## Стек и запуск

| | |
|---|---|
| Frontend | React 18 + Vite 5, **JavaScript без TypeScript** — точка входа `src/main.jsx` |
| Данные и вход | Supabase (Postgres + Auth), `@supabase/supabase-js` ^2.45 |
| Способ входа | **magic link**, а не пароль — см. [DECISIONS.md](DECISIONS.md) |
| Графики | `recharts` ^3.9 |
| Иконки | `lucide-react` ^0.383 |
| Деплой | `npm run deploy` → `vite build && gh-pages -d dist` |

Чего в стеке **нет** — это факты из [package.json](package.json), не догадки:

- **Роутера нет.** `react-router` отсутствует в зависимостях. Значит либо всё на
  одном экране, либо экраны переключаются состоянием, без URL. Проблемы
  GitHub Pages с путями (`HashRouter` vs `404.html`), которая съела время в
  networth-tracker, здесь просто не возникает ‹проверить по src/›.
- **Линтера и тестов нет.** Ни в `devDependencies`, ни в `scripts`. `npm run
  build` — это чистый `vite build`, без `tsc -b` и без проверок.
- **CI нет.** Ветка `gh-pages` пушится вручную с машины владельца пакетом
  `gh-pages`, а не GitHub Actions. Следствие: секретов в GitHub нет, ключи
  Supabase берутся из локального `.env` в момент сборки на машине.

Схема БД лежит в корне как [schema.sql](schema.sql) — не в `supabase/`, как у
соседнего проекта.

## Архитектура данных

Две таблицы, обе в `public`, обе с `user_id` и RLS. Дословно из
[schema.sql](schema.sql):

```sql
create table public.habits (
  id          uuid primary key default gen_random_uuid(),
  user_id     uuid not null default auth.uid() references auth.users(id) on delete cascade,
  name        text not null,
  sort_order  int  not null default 0,
  created_at  timestamptz not null default now()
);

create table public.completions (
  habit_id  uuid not null references public.habits(id) on delete cascade,
  user_id   uuid not null default auth.uid() references auth.users(id) on delete cascade,
  day       date not null,
  primary key (habit_id, day)
);
```

### Галочка — это существование строки

Главное в модели. У `completions` **нет булева поля** `done`/`completed`.
Одна строка = (привычка, день), и она либо есть, либо её нет:

- отметил день → `insert`;
- снял отметку → `delete`;
- «выполнено?» → строка существует.

Составной первичный ключ `(habit_id, day)` делает повторную отметку одного дня
**физически невозможной** — вторая вставка упирается в нарушение PK. Проверять
уникальность на клиенте не нужно, база не даст ошибиться.

`user_id` в `completions` продублирован (в `habits` он и так есть). Это нужно,
чтобы RLS-политика проверяла владельца по своей же строке, без join к `habits`
на каждый запрос. ‹Причина реконструирована по форме политики, а не
задокументирована.›

`default auth.uid()` в обеих таблицах — клиент не передаёт `user_id` при вставке
вообще, Postgres подставляет владельца сессии сам.

### RLS

```sql
alter table public.habits      enable row level security;
alter table public.completions enable row level security;

create policy "own habits" on public.habits
  for all using (auth.uid() = user_id) with check (auth.uid() = user_id);
-- то же самое для completions
```

Одна политика `for all` на таблицу — покрывает select/insert/update/delete
разом. `using` отвечает за то, какие строки видно, `with check` — за то, какие
можно записать. Без сессии `auth.uid()` = null, ни одна строка не проходит.

### Чего в модели нет

Это не «не успели», это границы инструмента. Каждый пункт = отсутствие колонки
в [schema.sql](schema.sql), проверяется чтением 37 строк файла:

- **Заметок к отметке.** Нельзя записать «пробежал 5 км» — только факт «сделано».
- **Стрика как хранимого поля.** Нет `streak`, `best_streak`, `current_streak`.
  Если серия дней где-то показывается — она считается на лету из `completions`
  ‹проверить по src/›.
- **Количественных целей.** Нет `target`/`amount`. «8 стаканов воды» выражается
  только как да/нет за день.
- **Архивации.** Нет `archived`, `is_active`, `deleted_at`. Привычку можно
  только удалить — и `on delete cascade` унесёт вместе с ней всю историю
  отметок безвозвратно.
- **Категорий, тегов, цветов, иконок.** У привычки есть ровно `name`.
- **Напоминаний.** Ни полей времени, ни расписания, ни чего-либо для пушей.
- **Частоты.** Нет «по будням» или «3 раза в неделю» — модель ежедневная,
  любой день можно отметить у любой привычки. Как это выглядит в интерфейсе —
  ‹проверить по src/›.
- **`created_at` у `completions`.** Известен день, за который стоит галочка, но
  не момент, когда её поставили. Отличить «отметил вечером» от «закрыл неделю
  задним числом» по базе нельзя.
- **Индексов кроме первичного ключа.** Для личного объёма данных неважно, но
  выборка «все отметки за месяц» идёт не по идеальному индексу: ведущая колонка
  PK — `habit_id`, а не `day`.
- **Уникальности имени привычки.** Две привычки с одинаковым `name` заведутся
  без возражений.
- **Осмысленного `sort_order` по умолчанию.** Он `not null default 0`, то есть
  у всех новых привычек одинаковый. Чем разрешается ничья при сортировке —
  ‹проверить по src/›.

### Ловушка: в схеме нет `GRANT`

В [schema.sql](schema.sql) **нет** ни одного `grant ... to authenticated`.
В networth-tracker это оказалось настоящей ошибкой `42501 permission denied
for table ...`: Supabase не выдаёт новым таблицам привилегий автоматически, и
Postgres режет запрос ещё до применения RLS.

Здесь проект работает. Значит гранты либо выданы вне файла (руками в SQL
Editor), либо сработали умолчания Supabase того времени. Что именно —
неизвестно ‹проверить в Supabase: `\dp public.habits` или Table Editor →
Policies/Privileges›.

Практический вывод один и он важнее причины: **схема не самодостаточна**.
Комментарий в её шапке обещает «вставь это целиком → Run», но у нового
человека на свежем проекте результат будет другим, чем был у владельца. Если
поднимать базу заново — сразу дописать:

```sql
grant select, insert, update, delete on public.habits, public.completions to authenticated;
```

и **не** выдавать те же права роли `anon`.

## Ключевые ограничения

- **Данные видны только после логина** — RLS на обеих таблицах
  (`auth.uid() = user_id`). Явных грантов в схеме нет, см. ловушку выше.
- **Вход только по magic link** — письмо со ссылкой. Пароля нет, значит нужен
  доступ к почте в момент входа. Оффлайн зайти нельзя.
- **Репозиторий публичный.** Это нормально: в коде из секретов только Supabase
  anon key, который по дизайну Supabase безопасен — доступ к данным реально
  ограничивает RLS, а не секретность ключа.
- **Отдельный Supabase-проект**, не общий с networth-tracker. Ключи в `.env`
  свои, база своя.
- **Удаление привычки необратимо** — cascade уносит всю историю отметок.
  Экспорта данных нет, бэкап возможен только через сам Supabase.
- **Деплой ручной.** Пуш в `main` ничего не публикует; публикует только
  `npm run deploy` с машины, где лежит рабочий `.env`.

## Как запустить локально

```bash
npm install

# .env в корне — нужны VITE_SUPABASE_URL и VITE_SUPABASE_ANON_KEY,
# образец в .env.example. Имена переменных ‹подтвердить по src/›.
# Схема БД — schema.sql, выполнить в Supabase → SQL Editor → New query → Run,
# плюс гранты для authenticated (см. «Ловушка» выше).

npm run dev      # дев-сервер
npm run build    # сборка в dist/
npm run preview  # посмотреть собранное локально
npm run deploy   # сборка + публикация в ветку gh-pages
```
