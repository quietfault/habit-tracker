# Habit Tracker — проектный файл для Claude Code

Общий контекст портфолио — в корневом `CLAUDE.md`. Корень портфолио это
**отдельный репозиторий `quietfault/root_main`** (приватный), а не каталог на
уровень выше: там же лежат `PROJECTS.md` (карта проектов, её обновляет
`/handoff`), `_brand/` и шаблоны. В сессии подключается через `add_repo`.
Брендбук живёт не в нём, а в `quietfault/marketing`, папка `brand/`.

> **Как написан этот файл.** Первая версия документации появилась 2026-08-14 и
> была восстановлена по [package.json](package.json), [index.html](index.html) и
> [schema.sql](schema.sql), **без чтения `src/`**. Из-за этого она массово врала:
> способ входа, механизм ключей, число таблиц, состав интерфейса. 2026-08-15
> каталог `src/` прочитан целиком, и файл переписан по коду. Пометки
> `‹проверить›` сняты — там, где факт подтверждён кодом, он так и записан.

## Что это

**Личная система целей.** Цели с этапами и сроками, задачи по матрице
Эйзенхауэра, ценности, журнал изменений, статистика — и привычки как один из
шести экранов.

**Имя историческое.** Проект начинался как трекер привычек и так и называется —
репозиторий, заголовок страницы, `package.json`. Менять имя решено не было:
ссылки, деплой и закладки уже привязаны. Но описывать проект как «трекер
привычек» неверно: `HabitTracker.jsx` — это корневой компонент-оболочка с
навигацией, а привычки занимают меньшую часть кода (`Goals.jsx` — 40 КБ,
`Tasks.jsx` — 23 КБ против экрана привычек внутри `HabitTracker.jsx`).

Интерфейс русский, тёмный, свёрстан под телефон (`maxWidth: 480`,
`viewport-fit=cover`).

Хронологически **первый проект портфолио** и первый опыт с Supabase и GitHub
Pages. `networth-tracker` ссылается на него как на уже имеющийся опыт.

Версия в `package.json` — `1.0.0`, задеплоен, используется ежедневно.

Оформление — по брендбуку `quietfault` (2026-08-17 — 08-18), см. «Оформление» ниже.
Часть его продублирована литералами в [index.html](index.html): фон `#0d1117`,
шрифтовой стек, `html, body, #root { height: 100% }`. Это единственное место,
где литерал допустим: стиль работает до загрузки бандла и существует ровно
затем, чтобы не было белой вспышки и скачка шрифта.

## Стек и запуск

| | |
|---|---|
| Frontend | React 18 + Vite 5, **JavaScript без TypeScript** — точка входа `src/main.jsx` |
| Данные и вход | Supabase (Postgres + Auth), `@supabase/supabase-js` ^2.45 |
| Способ входа | **email + пароль** (`signInWithPassword` / `signUp`), см. [DECISIONS.md](DECISIONS.md) |
| Графики | `recharts` ^3.9 — экран «Статистика» |
| Иконки | `lucide-react` ^0.383 |
| Шрифты | `@fontsource-variable/inter` + `@fontsource/jetbrains-mono` — самохостятся, CDN запрещён брендбуком |
| Деплой | `npm run deploy` → `vite build && gh-pages -d dist` |

Чего в стеке **нет**:

- **Роутера нет.** `react-router` отсутствует в зависимостях, и это не «всё на
  одном экране»: шесть экранов переключаются состоянием `view` в
  `src/HabitTracker.jsx` (`useState("today")`), без URL. Следствие — на любой
  экран нельзя дать ссылку, обновление страницы всегда возвращает на привычки,
  кнопка «назад» браузера выходит из приложения. Взамен проблемы GitHub Pages с
  путями (`HashRouter` vs `404.html`), съевшей время в networth-tracker, здесь
  не возникает вообще.
- **Линтера и тестов нет.** Ни в `devDependencies`, ни в `scripts`. `npm run
  build` — чистый `vite build`, без `tsc -b` и без проверок.
- **CI нет.** Ветка `gh-pages` пушится вручную с машины владельца пакетом
  `gh-pages`, а не GitHub Actions. Секретов в GitHub заводить не нужно — ключи и
  так лежат в коде (см. ниже).

Схема БД лежит в корне как [schema.sql](schema.sql) — не в `supabase/`, как у
соседнего проекта. И она **устарела**, см. «Архитектура данных».

### Ключи Supabase — в коде, а не в `.env`

Это главное расхождение с соседним проектом и с первой версией этой
документации. Фактически:

- **`.env` в проекте не используется.** Ни одного `import.meta.env` в `src/`
  нет. Файла `.env` никогда не существовало и в историю репозитория он не
  попадал (проверено 2026-08-15).
- Оба значения зашиты константами в
  [src/supabaseClient.js](src/supabaseClient.js): `SUPABASE_URL` и
  `SUPABASE_PUBLISHABLE_KEY` формата `sb_publishable_...` — это **новый формат
  публичного ключа Supabase**, пришедший на смену `anon`-ключу.

**Утечки здесь нет, и ротация не нужна.** Publishable-ключ публичен по дизайну:
он в любом случае уезжает в собранный бандл и виден каждому, кто откроет сайт.
Доступ к данным ограничивает Row Level Security в базе, а не секретность ключа.
Секретным является только `sb_secret_...`, и его в браузерном коде нет и быть не
может — об этом прямо написано в комментарии самого файла.

### Деплой и `base`

В [vite.config.js](vite.config.js) стоит `base: "./"` — пути к ассетам
относительные, поэтому сборка работает под любым именем репозитория на
GitHub Pages. **Править `base` не нужно**, в том числе при переименовании репы;
жёстко прописанное `'/habit-tracker/'` только создало бы риск белого экрана.

Remote — `https://github.com/quietfault/habit-tracker.git`, через дефис, по
правилу портфолио. Публичный адрес: `https://quietfault.github.io/habit-tracker/`.

## Архитектура данных

### ⚠️ `schema.sql` устарел относительно кода

В [schema.sql](schema.sql) описаны **две** таблицы — `habits` и `completions`.
Приложение работает с **двенадцатью**. Более того, даже у `habits` в файле не
хватает колонок, которые код читает и пишет: `group_id` и `target_per_week`.

Это значит: **поднять базу с нуля по `schema.sql` нельзя** — приложение
упадёт. Файл годится только как исторический документ.

Реальный набор таблиц (собран по всем вызовам `supabase.from(...)` в `src/`):

| Таблица | Экран | Что хранит |
|---|---|---|
| `habits` | Привычки | привычка: `name`, `sort_order`, `group_id`, `target_per_week` |
| `completions` | Привычки | отметка (привычка, день) |
| `groups` | Привычки | категории привычек |
| `goals` | Цели | цель: `name`, `target_date`, `status`, `group_id`, `sort_order` |
| `goal_groups` | Цели | группы целей |
| `goal_stages` | Цели | этапы цели: `goal_id`, `name`, `status`, `sort_order` |
| `goal_events` | Цели, Лог | журнал изменений целей |
| `goal_habit_links` | Цели | связь цель/этап ↔ привычка |
| `goal_value_links` | Цели, Ценности | связь цель ↔ ценность |
| `values_list` | Ценности | ценности: `name`, `description`, `sort_order` |
| `tasks` | Задачи | задача: `triaged`, `important`, `urgent`, срок, `sort_order` |
| `subtasks` | Задачи | подзадачи |

**Что надо сделать:** выгрузить актуальный DDL из Supabase (SQL Editor →
`pg_dump`-подобный запрос по `information_schema`, либо Database → Schema Visualizer
→ экспорт) и **перезаписать `schema.sql` целиком**, вместе с политиками RLS и
грантами. До этого момента файл читать как «как всё начиналось», а не как
инструкцию.

Ниже — то, что в файле есть сейчас, дословно:

```sql
create table public.habits (
  id          uuid primary key default gen_random_uuid(),
  user_id     uuid not null default auth.uid() references auth.users(id) on delete cascade,
  name        text not null,
  sort_order  int  not null default 0,
  created_at  timestamptz not null default now()
);

create table public.completions (
  habit_id  uuid not null references public.habits(id) on delete cascade,
  user_id   uuid not null default auth.uid() references auth.users(id) on delete cascade,
  day       date not null,
  primary key (habit_id, day)
);
```

### Галочка — это существование строки

Главное в модели привычек. У `completions` **нет булева поля** `done`/`completed`.
Одна строка = (привычка, день), и она либо есть, либо её нет:

- отметил день → `insert`;
- снял отметку → `delete`;
- «выполнено?» → строка существует.

Составной первичный ключ `(habit_id, day)` делает повторную отметку одного дня
**физически невозможной** — вторая вставка упирается в нарушение PK. Проверять
уникальность на клиенте не нужно, база не даст ошибиться.

`user_id` в `completions` продублирован (в `habits` он и так есть). Это нужно,
чтобы RLS-политика проверяла владельца по своей же строке, без join к `habits`
на каждый запрос. ‹Причина реконструирована по форме политики.›

`default auth.uid()` — клиент не передаёт `user_id` при вставке вообще, Postgres
подставляет владельца сессии сам. То же самое во всех остальных таблицах.

### RLS

```sql
alter table public.habits      enable row level security;
alter table public.completions enable row level security;

create policy "own habits" on public.habits
  for all using (auth.uid() = user_id) with check (auth.uid() = user_id);
-- то же самое для completions
```

Одна политика `for all` на таблицу — покрывает select/insert/update/delete
разом. `using` отвечает за то, какие строки видно, `with check` — за то, какие
можно записать. Без сессии `auth.uid()` = null, ни одна строка не проходит.
Аналогичные политики стоят на остальных десяти таблицах — иначе приложение бы не
работало, но в `schema.sql` их нет.

### Что есть в модели привычек

- **Категории.** Таблица `groups` + `habits.group_id`. Привычка либо в группе,
  либо в «без группы». Группы сворачиваются, состояние свёрнутых лежит в
  `localStorage` под ключом `ht-collapsed-groups`. Есть «свернуть/развернуть
  всё». Цветов и иконок у групп нет — только имя и порядок.
- **Частота.** Колонка `habits.target_per_week` (1–7) и константа `TARGETS` в
  `src/HabitTracker.jsx`: «Ежедневно» = 7, дальше «1×/нед»…«6×/нед».
  Привычка с `target_per_week < 7` считается недельной (`isWeekly`), и для неё
  интерфейс показывает не дневную галочку, а счётчик `выполнено/цель на неделе`
  плюс **недельный стрик** — сколько недель подряд цель выдержана
  (`countInWeekOf`, `weeklyStreak`). Ежедневные и недельные привычки разведены:
  прогресс-бар «N / M сегодня» считается только по ежедневным.
- **Ручной порядок.** `sort_order`, см. ниже.
- **Связь с целями.** `goal_habit_links` — привычку можно привязать к цели или к
  её этапу, и на экране целей рядом с целью показывается прогресс по привычке.

### Чего в модели привычек нет

Это границы инструмента, а не «не успели»:

- **Заметок к отметке.** Нельзя записать «пробежал 5 км» — только факт «сделано».
- **Стрика как хранимого поля.** Нет `streak`, `best_streak`. Серии считаются на
  лету из `completions` — функции `streak` и `weeklyStreak` в
  `src/HabitTracker.jsx`.
- **Количественных целей.** Нет `target`/`amount` внутри дня. «8 стаканов воды»
  выражается только как да/нет за день (частота — про недели, не про день).
- **Архивации.** Нет `archived`, `is_active`, `deleted_at`. Привычку можно
  только удалить — и `on delete cascade` унесёт вместе с ней всю историю
  отметок безвозвратно.
- **Цветов и иконок.** Ни у привычки, ни у группы. Категории при этом есть.
- **Напоминаний.** Ни полей времени, ни расписания, ни чего-либо для пушей.
- **Конкретных дней недели.** `target_per_week` — это «сколько раз за неделю», а
  не «по понедельникам и четвергам». Любой день недели засчитывается одинаково.
- **`created_at` у `completions`.** Известен день, за который стоит галочка, но
  не момент, когда её поставили. Отличить «отметил вечером» от «закрыл неделю
  задним числом» по базе нельзя.
- **Уникальности имени привычки.** Две привычки с одинаковым `name` заведутся
  без возражений.

### Как на самом деле работает `sort_order`

Ничьей при сортировке не возникает, вопреки тому, что можно было предположить по
`default 0` в схеме: **клиент никогда не полагается на умолчание**. При
добавлении привычки `src/HabitTracker.jsx` считает
`maxSort = max(sort_order по всем привычкам)` и вставляет с `maxSort + 1` — новая
привычка всегда уезжает в конец списка.

Порядок меняется **стрелками вверх/вниз в режиме «Править»**, а не
drag-and-drop. Механика — своп: `moveHabit` находит соседа внутри той же группы
(по отсортированному списку), меняет местами значения `sort_order` двумя
`update`-запросами и одновременно правит локальный стейт. Переставить привычку
между группами стрелками нельзя — группа меняется отдельным селектом.

Та же схема (max+1 при вставке, своп стрелками) применяется к целям, этапам
целей, задачам и ценностям — см. `Goals.jsx`, `Tasks.jsx`, `Values.jsx`.

### Ловушка: в схеме нет `GRANT`

В [schema.sql](schema.sql) **нет** ни одного `grant ... to authenticated`.
В networth-tracker это оказалось настоящей ошибкой `42501 permission denied
for table ...`: Supabase не выдаёт новым таблицам привилегий автоматически, и
Postgres режет запрос ещё до применения RLS.

Здесь проект работает. Значит гранты либо выданы вне файла (руками в SQL
Editor), либо сработали умолчания Supabase того времени. Что именно —
неизвестно ‹проверить в Supabase: `\dp public.habits` или Table Editor →
Policies/Privileges›.

Практический вывод один и он важнее причины: **схема не самодостаточна** —
и по грантам, и по составу таблиц. Когда её будут перезаписывать из Supabase,
гранты надо включить в выгрузку:

```sql
grant select, insert, update, delete on public.habits, public.completions to authenticated;
```

и **не** выдавать те же права роли `anon`.

Светлые значения у них не выведены: переключателя тем в приложении нет.
Пока его нет, `[data-theme="light"]` работать не будет.

### Знак в интерфейсе

«Пересборка» стоит в трёх местах: фавиконка и `apple-touch-icon` (через
`index.html`), знак 48px над заголовком на экране входа и знак 16px слева от
даты в шапке приложения. «Разлом» не используется нигде — §3 запрещает его в
представительских местах, а внутренних инструментов у приложения нет.

Вставлять знак только через `<Mark size={...} />`. Компонент держит два
правила брендбука, которые иначе забываются:

1. **Размер кратен 16.** Высота полосы — `size × 4/64`, поэтому 16px даёт
   ровно 1px, 32px — 2px, 48px — 3px. «Почти такой же» 20px даёт 1.25px, край
   попадает между пикселями, и знак мылится. Некратный размер роняет сборку
   исключением — это дешевле, чем заметить мыло на телефоне.
2. **Охранное поле** — четверть высоты знака со всех сторон, считается от
   занимаемых 40 единиц из 64, а не от размера квадрата.

Берётся вариант `--dark`: цвета зашиты в файл, поэтому его можно отдавать
через `<img>`. С `--mono` так нельзя — `currentColor` через тег картинки не
наследуется, знак станет чёрным.

### Две ловушки, на которые легко наступить

1. **Конкатенация альфы к цвету.** Раньше писали `C.gold + "22"` — с
   `var(--accent)` это молча даёт мусор. Для прозрачных вариантов есть
   `C.accentSoft` (заливка) и `C.accentEdge` (граница).
2. **Цвета в SVG.** `recharts` и `lucide-react` кладут цвет в презентационные
   атрибуты. У иконок это решено через `currentColor`: цвет задаётся
   `style={{ color: ... }}`, а не пропом `color`. У графиков — через `paint()`,
   который отдаёт вычисленные значения вместо ссылок.

### Чего по брендбуку ещё не сделано

Акцент используется чаще, чем разрешает §4 («не больше одного оранжевого
элемента в блоке»); шкала кеглей `--step-*` и `--maxw` не применены — они
рассчитаны на маркетинговый сайт; `--radius: 14px` не разведён по компонентам.
Подробности — в [STATUS.md](STATUS.md).

## Экраны и UX

Роутера нет. Всё приложение — один URL, экраны переключаются состоянием `view` в
`src/HabitTracker.jsx`. Сегментированный переключатель наверху: три экрана
видимы всегда, ещё три спрятаны под «Ещё».

Неавторизованному показывается **`src/Auth.jsx`** — экран входа: два поля
(email, пароль), кнопка «Войти» и текстовая кнопка-переключатель «Нет аккаунта —
зарегистрироваться». `src/App.jsx` слушает `onAuthStateChange` и подменяет
`Auth` на `HabitTracker`, как только появляется сессия.

| Экран | `view` | Файл | Что там |
|---|---|---|---|
| **Цели** | `goals` | `Goals.jsx` | Цели в группах, у каждой — этапы, срок, статус по циклу «не начата → в работе → выполнена». Цель связывается с привычками и с ценностями. Внутри цели — мини-история из `goal_events`. |
| **Задачи** | `tasks` | `Tasks.jsx` | Матрица Эйзенхауэра: инбокс «Не разобрано» + четыре квадранта (срочно/важно). Подзадачи, сроки, массовое выделение, скрытие выполненных. |
| **Привычки** | `today` | `HabitTracker.jsx` | Экран по умолчанию. Счётчик «N / M сегодня» и прогресс-бар по ежедневным привычкам, сетка последних 7 дней, стрик, группы со сворачиванием, режим «Править» (переименование, группа, частота, стрелки порядка, удаление). |
| **Ценности** | `values` | `Values.jsx` | Список ценностей с описанием. Обратная связь: у каждой ценности видно, какие цели на неё завязаны и в каком они статусе. |
| **Лог** | `feed` | `Feed.jsx` | Журнал изменений целей из `goal_events`, сгруппированный по дням («Сегодня», «Вчера», дата). Типы событий и их иконки — в `events.jsx`. |
| **Статистика** | `stats` | `Stats.jsx` | Единственное место, где используется `recharts`. Периоды 7/30/90 дней, разбивка по группам с «проваливанием» внутрь, два режима графика (накопительный и скользящее среднее за 7 дней). Недельные привычки нормализуются (`target_per_week / 7` в день). |

Общие приёмы интерфейса, повторяющиеся на всех экранах: режим «Править» вместо
постоянно видимых кнопок удаления, сворачиваемые группы с состоянием в
`localStorage` (`ht-collapsed-groups`, `gt-collapsed-groups`, `tk-collapsed`),
оптимистичный апдейт (стейт правится сразу, запрос уходит следом), перезагрузка
данных по `visibilitychange` — вернулся во вкладку, данные свежие.

## Ключевые ограничения

- **Регистрация в Supabase закрыта, кнопка в интерфейсе оставлена намеренно.**
  Self-signup выключен давно и включается вручную на то время, пока нужно
  завести аккаунт (со слов владельца, 2026-08-20). Поэтому переключатель «Нет
  аккаунта — зарегистрироваться» в `src/Auth.jsx` не лишний: он и нужен в тот
  момент. Пока регистрация закрыта, форма отвечает ошибкой Supabase.

  **До 2026-08-20 здесь было написано обратное** — «self-signup не выключен,
  любой посетитель заводит аккаунт», — и то же самое стояло в `STATUS.md`,
  `README.md`, `DECISIONS.md` и летописи. Утверждение появилось 2026-08-15
  реконструкцией и ни разу не проверялось: консоль Supabase доступна только
  владельцу, из сессии её не видно. Пять дней документация пугала дырой,
  которой нет.
- **Данные видны только после логина** — RLS по `auth.uid() = user_id`. Явных
  грантов в схеме нет, см. ловушку выше.
- **Вход по email и паролю.** Восстановления пароля в интерфейсе нет — если
  пароль забыт, сбрасывать через Supabase.
- **Репозиторий публичный, ключи Supabase лежат прямо в коде.** Это нормально:
  `sb_publishable_...` публичен по дизайну, доступ ограничивает RLS. Секретный
  `sb_secret_...` в браузерный код не попадает никогда.
- **Отдельный Supabase-проект**, не общий с networth-tracker.
- **Удаление необратимо** — cascade уносит связанные строки (историю отметок у
  привычки, этапы и связи у цели). Экспорта данных нет, бэкап возможен только
  через сам Supabase.
- **Нет ссылок на экраны.** Роутера нет, поэтому поделиться ссылкой на
  конкретную цель невозможно, а обновление страницы всегда открывает привычки.
- **Деплой ручной.** Пуш в `main` ничего не публикует; публикует только
  `npm run deploy` с машины владельца.

## Как запустить локально

```bash
npm install

# .env не нужен: ключи Supabase зашиты в src/supabaseClient.js.
# Схема БД — актуальную выгружать из Supabase; schema.sql в репозитории устарел
# (описывает 2 таблицы из 12), см. «Архитектура данных».

npm run dev      # дев-сервер
npm run build    # сборка в dist/
npm run preview  # посмотреть собранное локально
npm run deploy   # сборка + публикация в ветку gh-pages
```

Чтобы подключиться к своему Supabase — править константы в
[src/supabaseClient.js](src/supabaseClient.js), а не заводить `.env`.
